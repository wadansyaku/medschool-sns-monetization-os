# 外部レビュー運用

## 目的

Codex を制作の主担当にしつつ、GitHub と Atlas を `第三者視点のレビュー層` として使う。目的は、方向性のズレと自己満足の量産を防ぐこと。

## 1. GitHub の使い方

### ローカル運用

- このディレクトリは Git 初期化済み
- ブランチ運用の基本:
  - `main`
  - `week-XX-topic-slug`
- 週の作業を始める時:
  - 週次パッケージ単位でブランチを切る
- 週の作業が終わった時:
  - PR テンプレートを埋める前提で差分を整理する

### GitHub 側でやること

- 新規リポジトリを作る
- このディレクトリをそのリポジトリへ push する
- 週次パッケージごとに PR を作り、レビュー単位を `1テーマ1パッケージ` に保つ
- PR の本文には `.github/pull_request_template.md` を使う

### GitHub で見る観点

- フックが弱くないか
- その企画が 3 レイヤーのどこに属するか明示されているか
- YouTube 長尺主軸が崩れていないか
- 再利用で主張がブレていないか
- CTA が主題を食っていないか
- AI が主役化していないか
- 禁止領域に触れていないか
- 次週に再現できる構造になっているか

## 2. Atlas の使い方

### Atlas に聞くべきタイミング

- 新しいコンテンツ柱を始める前
- 新しいレイヤー配分を試す前
- 2週間以上、長尺の反応や回遊が伸びない時
- 価格や商品の見せ方を変える前
- バズったが登録や長尺視聴につながらなかった投稿の原因を考える時

### Atlas に渡す最小セット

- `AGENTS.md`
- `01_strategy/strategy_hub.md`
- 対象の週次パッケージ
- 直近の `03_analytics_os/weekly_review.md`
- 聞きたいことを 3 つ以内に絞った質問文

### Atlas に投げる質問例

- `この核テーマは、新ブランドのどのレイヤーとして十分に成立していますか`
- `この長尺は、登録理由になる強さがありますか`
- `この短尺4本の切り口は、同じ主張の別角度として成立していますか`
- `再生は取れても長尺視聴や登録につながらない場合、どこを疑うべきですか`

### Atlas の助言の扱い

- そのまま採用しない
- `長尺テーマが強くなるか`
- `このアカウントのブランドと一致するか`
- `継続運用できるか`
- 上の 3 点で判断してから採用する
- 結果は `03_analytics_os/advice_log.md` に残す

## 3. 推奨レビュー順

1. Codex で核テーマとパッケージを作る
2. 自分で 5 分だけ読んで、ズレを消す
3. Atlas に `方向性` と `レイヤー` を見てもらう
4. GitHub PR にまとめて、差分単位で見返せるようにする
5. 採用した指摘だけを反映し、翌週の運用へ持ち込む

## 4. 判断ルール

- Codex と Atlas の意見が割れたら:
  - 長尺テーマとして強い方を優先
  - 3 レイヤーにきれいに収まる方を優先
  - 継続制作しやすい方を優先
  - 極端な路線変更は 1 週ではやらない
- GitHub PR で残すべきこと:
  - 何を変えたか
  - なぜ変えたか
  - どの助言を採用し、何を見送ったか

## 5. 今後追加すると良いもの

- GitHub Issues で `試す仮説` を管理する
- PR のラベルを `hook` `cta` `offer` `analytics` に分ける
- Atlas 用の質問テンプレートを勝ちパターン別に増やす
